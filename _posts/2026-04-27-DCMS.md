## Chapter One — Introduction

### 1.1 Background

The healthcare industry, particularly specialised fields like dentistry, relies heavily on efficient administrative and clinical processes to ensure high-quality patient care. Traditional dental clinics often manage core operations — such as appointment scheduling, patient record-keeping, treatment charting, and billing — using manual paper-based methods or fragmented digital tools such as spreadsheets and basic word-processing documents.

The client, **Dr. Smile Dental Clinic**, is a single-location practice offering general and cosmetic dentistry services. Prior to this project, operations were conducted as follows:

- Appointments were managed on a **physical daily planner**
- Patient records were stored in **physical file folders**
- Billing was calculated manually and recorded in a **spreadsheet**

This reliance on manual and semi-digital systems created inefficiencies, increased the risk of human error, and limited the clinic's ability to analyse performance — setting the stage for critical problems related to data integrity, patient service delivery, and operational efficiency that this project intends to solve.

---

### 1.2 Problem Statement

The existing operational methods presented several critical problems that impeded efficiency and patient care quality:

**1. Inefficient and Error-Prone Appointment Scheduling**
Appointments were managed manually on a paper ledger, making it difficult to check real-time slot availability. This led to frequent double-bookings, conflicts between multiple practitioners, and a high rate of missed appointments due to the lack of automated reminders.

**2. Insecure and Inaccessible Patient Data (EHR)**
Patient records, including medical history and clinical notes, were stored in physical files. Retrieval was slow, posed a security risk, and prevented immediate chairside access to critical data such as X-rays or past treatment plans during consultations.

**3. Lack of Standardised Clinical Documentation**
The manual process lacked an interactive odontogram (tooth chart), making the charting of procedures subjective, inconsistent, and time-consuming — increasing effort and complicating communication between dental professionals.

**4. Cumbersome Billing and Financial Reporting**
Invoicing was done manually using procedure codes and basic spreadsheet calculations. The process was time-consuming, increased billing error likelihood, and prevented the swift generation of financial reports needed for business analysis.

---

### 1.3 Objectives

The main objective of this project is to develop a **Dental Clinic Management System (DCMS)** to streamline operations and enhance the quality of patient care within the dental practice.

#### System Objectives (SMART)

| Objective | Description |
|---|---|
| Scheduling | Reduce appointment scheduling conflicts through the implementation of a real-time, multi-user scheduling interface with automated conflict detection. |
| EHR Retrieval | Enable instant, secure retrieval of any patient's complete Electronic Health Record (EHR) within 5 seconds by digitalising all records and implementing efficient database querying. |
| Clinical Charting | Standardise and accelerate clinical charting by deploying an interactive odontogram component that visualises procedure history, reducing charting time per patient. |
| Billing | Automate invoice generation and provide accurate, consolidated monthly revenue reports in real-time for financial analysis. |

#### Research Objectives

- To identify the existing problems and precise functional requirements of a typical small-to-medium-sized dental clinic through interviews with practitioners and administrative staff.
- To investigate and select the optimal technology stack (front-end framework, back-end API, database) suitable for a secure and scalable web-based DCMS.
- To design the logical and physical database structure (Entity-Relationship Diagram) necessary to support the complex relationships of patient records, treatments, and billing data.
- To develop and implement the core DCMS modules, including Appointment Scheduling, EHR with Odontogram, and Billing, using best-practice software development methodologies.
- To conduct thorough functional and user acceptance testing (UAT) to ensure the system meets all specified requirements and performs reliably under typical clinic load.

## Chapter Two — Literature Review & Requirements

### 2.1 Literature Review

The effective management of patient information and clinic operations is crucial for the modern dental practice. This literature review analyses the current landscape of Dental Practice Management Software (PMS) to understand existing capabilities, identify technological trends, and pinpoint critical gaps that the proposed DCMS is designed to address. The review focuses on three main categories of existing solutions: high-end commercial, community-driven open-source, and specialised small-scale systems.

#### 2.1.1 Analysis of Existing Practice Management Systems

| System | Organisation | Key Features | Limitations & Gaps |
|---|---|---|---|
| **Dentrix Ascend** | Henry Schein | Comprehensive cloud-based platform with extensive EHR, integrated charting, advanced billing, and imaging integration. Suitable for large multi-site groups. | High subscription-based cost; complex feature set requiring extensive training; high Total Cost of Ownership making it inaccessible for small clinics. |
| **OpenMolar** | Open Source Community | Free-to-use; basic appointment management; cross-platform compatibility (Linux, Windows); focuses on core record-keeping. | Requires significant internal technical expertise; lacks modern UX/UI; interactive Odontogram is basic or non-functional. |
| **Clear.Dental** | Clear.Dental (Example PMS) | Linux compatibility; basic touch-friendly interface; optimised for specific niche hardware setups. | Architectural over-specification (e.g., requiring a distributed file system) is unnecessary overhead for a single-site practice, increasing infrastructure cost. |

#### 2.1.2 Analysis of Key Component Gaps

**Security and Regulatory Compliance in EHR:**
The literature strongly emphasises the necessity of robust security architecture for managing sensitive patient data (Nowrozy et al., 2024). The existing manual systems at the clinic fail entirely in data integrity, unauthorised access prevention, and audit logging. The proposed DCMS prioritises a security-by-design approach — including Role-Based Access Control (RBAC) and data encryption — as a foundational, non-negotiable feature.

**The Interactive Odontogram Requirement:**
The clinical charting component is a core differentiator. Advanced dental informatics research highlights the significant efficiency gain when the Odontogram allows direct visual interaction and instant history visualisation, reducing documentation time per patient (Dental Informatics Review, 2020). Implementing a custom dynamic Odontogram using PHP/MySQL and SVG was a critical technical objective of this project.

#### 2.1.3 Synthesis and Justification

The review identifies a critical market gap: the absence of an affordable, feature-rich PMS specifically optimized for the constraints of a small, single-location dental practice. Commercial systems offer robust features at unjustifiable expense and complexity, while open-source solutions are affordable but lack the professional finish, sophisticated reporting, and critical interactive features necessary for modern clinical efficiency.

The DCMS bridges this gap by providing a highly customised, cost-effective, web-based solution that balances security and data integrity with a simple, responsive, and intuitive user interface.

## Chapter Three — Design & Implementation

### 3.1 Data Collection Methods

The **Enhanced Waterfall Model** was adopted for this project. The research methodology employed multiple data-collection approaches to ensure a comprehensive understanding of the clinic's operational requirements:

- **Structured Interviews:** Conducted with the client dentist, hygienists, and reception staff to gather detailed functional and non-functional requirements and understand current workflow pain points.
- **Document Analysis:** Review of existing paper forms (patient intake forms, billing receipts) and spreadsheet data structures to understand required data fields and entity relationships.
- **Direct Observation:** Observing current patient flow and administrative processes to identify bottlenecks in appointment scheduling and record retrieval.

A **purposive sampling strategy** was employed, selecting all key staff members (Dentist, Hygienist, Receptionist, Administrator) at Dr. Smile Dental Clinic who interact with the existing system or who would be primary users of the proposed DCMS.

---

### 3.2 Systems Design Specifications

The SDS translates the high-level requirements from the SRS into a detailed blueprint for implementation, covering system architecture, module breakdown, data structures, and interface designs.

#### 3.2.1 System Architecture — Three-Tier Web Architecture

| Layer | Component / Technology | Rationale |
|---|---|---|
| **Presentation (Client)** | PHP/HTML5/CSS3/JavaScript with 'Hygienic Blue' design theme | Fully responsive; accessible via standard web browsers. |
| **Application (Logic)** | PHP 8.2 Backend with PDO prepared statements | Handles all business logic, RBAC enforcement, and data validation. |
| **Data (Storage)** | MySQL Community Edition | Relational integrity for complex EHR/Billing relationships. |
| **Infrastructure** | Cloud / XAMPP (Local) with HTTPS/TLS | Secure web-based delivery; scalable; ngrok tunnel for M-Pesa callbacks. |

#### 3.2.2 Database Design

The database was designed using normalisation principles to eliminate redundancy and maintain data integrity. Key tables and their relationships are summarised below:

| Table | Primary Key | Key Fields / Foreign Keys |
|---|---|---|
| `patients` | `patient_id` (INT, AUTO_INCREMENT) | full_name, date_of_birth, phone, email, gender, address |
| `staff` | `id` (INT) | username, password (bcrypt hash), role (Admin/Dentist/Receptionist), status |
| `appointments` | `id` (INT) | patient_id (FK), dentist_id (FK), appointment_date, appointment_time, status, notes |
| `odontogram_entries` | `id` (INT) | appointment_id (FK), patient_id (FK), tooth_number (FDI), surface, procedure_code (FK), status |
| `invoices / mpesa_transactions` | `id` (INT) | appointment_id (FK), amount, status (Paid/Pending), mpesa_receipt |
| `inventory` | `id` (INT) | item_name, category, quantity, min_stock_level, unit |

#### 3.2.3 Modular Software Design

| Module | Sub-Modules / Functions |
|---|---|
| **P1: Appointment Module** | CRUD Appointment (F-1.4), Conflict Check (F-1.2), Send Reminder (F-1.3) |
| **P2: EHR & Charting Module** | Patient Registration (F-2.2), Patient Search (F-2.3), Clinical Notes (F-2.1), Odontogram Update (F-3.2, F-3.3) |

#### 3.2.4 Double-Booking Prevention Logic (F-1.2)

The following pseudocode enforces the mandatory requirement to prevent overlapping appointments for the same practitioner:

```
FUNCTION CreateAppointment(PatientID, DentistID, StartTime):
  IF DentistID IS NULL OR StartTime IS NULL THEN
    RETURN 'Error: Mandatory fields required.'
  END IF

  QUERY: SELECT id FROM appointments
    WHERE dentist_id = DentistID
    AND ABS(TIMESTAMPDIFF(MINUTE, appointment_time, StartTime)) < 30
    AND status NOT IN ('Cancelled')

  IF conflict found THEN
    RETURN 'Conflict Detected: Overlapping booking prevented.'
  ELSE
    INSERT INTO appointments (...) VALUES (...)
    RETURN 'Appointment successfully scheduled.'
  END IF
```

### 3.3 Test Plan

A hybrid testing strategy was adopted combining **Manual, Functional, Regression, and Boundary** testing across three testing levels:

**Unit Testing:**
Individual PHP functions and PDO database operations tested in isolation — including prepared statements for INSERT/UPDATE/SELECT, session role validation guards, TIMESTAMPDIFF conflict detection, and M-Pesa phone number formatting.

**Integration Testing:**
Module-to-module communication verified — Receptionist check-in to Dentist queue, procedure entry to Odontogram colour update to Invoice line item, M-Pesa STK Push to Safaricom callback to payment confirmation.

**System Testing:**
End-to-end workflows simulating real clinic operation — full patient journey (Register → Book → Check-in → Treat → Complete → Invoice → Pay), admin reporting pipeline, and role-mismatch guard validation.

## Chapter Five — Conclusions & Recommendations

### 5.1 Conclusions

The Dr. Smile Dental Clinic Management System (DCMS) was successfully designed, developed, and tested as a fully functional web-based application. The system fulfils all primary objectives set out in Chapter One:

- **Appointment scheduling conflicts have been eliminated** through the real-time conflict detection engine (TIMESTAMPDIFF ± 30-minute buffer), validated in TC003 and the integration testing phase.
- **Patient Electronic Health Records can be retrieved instantly** from any module, meeting the 5-second retrieval requirement specified in the SRS (F-2.3, Section 2.2).
- **Clinical charting has been standardised** through the deployment of the anatomical SVG Odontogram using the FDI two-digit numbering system, colour-coded by treatment status (Green/Yellow/Red).
- **Invoice generation is now fully automated** — triggered immediately when an appointment status is set to Completed — and integrated with the M-Pesa Daraja STK Push payment gateway for cashless transactions.
- **All 18 formal test cases passed** with zero critical outstanding defects. The two identified bugs (BUG-019, BUG-020) were resolved and verified through regression testing.
- **UAT feedback yielded an average usability rating of 4.5/5**, exceeding the SRS target of a SUS score ≥ 70, confirming high user acceptance across all three role groups.

### 5.3 Recommendations

Based on the findings, testing outcomes, and user feedback collected during this project, the following enhancements are recommended for future versions of the DCMS:

1. **AJAX/WebSocket Real-Time Queue Updates:** Replace the current 2-minute auto-refresh on the Dentist dashboard with WebSocket or long-polling to provide instant queue updates for both Reception and Dentist dashboards without manual page refreshes.

2. **Mobile-Responsive Redesign:** Implement card-based table layouts for screens below 768px to resolve the overflow issues identified in UAT (Mobile/Tablet rating: 3.8/5).

3. **Predictive Financial Analytics:** Add 30-day revenue forecasting on the Admin Executive Dashboard, based on historical appointment density and procedure revenue trends.

4. **Africa's Talking SMS Reminders:** Integrate Africa's Talking API or a Kenyan bulk SMS gateway for automated 24-hour appointment reminders, replacing the current manual notification process.

5. **Prescription Module:** Add a prescription management feature within the treatment session, enabling dentists to issue and print prescriptions directly from `treat.php`.

6. **Server-Side PDF Export:** Replace browser print-dialog dependency with a server-side PDF library (TCPDF or Dompdf) for generating invoices and reports as downloadable PDFs.

7. **Audit Trail Logging:** Implement an `audit_log` table recording all status changes, logins, and billing events for regulatory compliance and accountability.

8. **Cloud Deployment:** Migrate from local XAMPP to a production cloud environment (e.g., DigitalOcean or AWS) with SSL certification, automated database backups, and a documented disaster recovery procedure.

The following table documents the complete role-based patient journey workflow as covered in the User Training Manual:

| Step | Action | Role | System Effect |
|---|---|---|---|
| 1 | Patient calls to book | Receptionist | Register new patient → record created in `patients` table. |
| 2 | Book appointment | Receptionist | Appointment created; status = Scheduled; dentist notified via dashboard. |
| 3 | Patient arrives | Receptionist | Click **Check In** → status = Checked-in; `check_in_time` stamped; queue updates. |
| 4 | Dentist reviews queue | Dentist | Patient appears in Clinical Dashboard queue with amber dot and wait timer. |
| 5 | Start treatment | Dentist | Click **Start** → `treat.php` opens; status = In-Progress; session timer begins. |
| 6 | Record procedures | Dentist | Quick Entry or Charting → `odontogram_entries` inserted; session total updates. |
| 7 | Add session notes | Dentist | Notes saved to `appointments.notes` for the specific visit record. |
| 8 | Complete session | Dentist | Click **Complete Session** → status = Completed; redirected to dashboard. |
| 9 | Process M-Pesa payment | Receptionist | Open Billing → enter amount → **Send STK Push** → patient enters PIN. |
| 10 | Payment confirmed | System | Safaricom callback fires → invoice status = Paid; receipt number stored. |
| 11 | Generate invoice | Receptionist | Invoice auto-displayed with receipt; **Print Invoice** for patient copy. |
| 12 | Review in reports | Administrator | Session and payment reflected in Financial and Appointments report tabs. |

// Maps Universal tooth IDs to anatomical SVG shape categories
if (in_array($tooth_id, [1,2,3,14,15,16,17,18,19,30,31,32])) {
    $category = 'molar';

#### Snippet B: M-Pesa STK Push Integration (`mpesa.php`)

Handles the sanitization of Kenyan phone numbers to the required format (254...) and triggers the Daraja API for real-time payments.

```php
// Format phone: 07XXXXXXXX → 2547XXXXXXXX
function formatPhone($phone) {
    if (substr($phone, 0, 1) === '0') {
        return '254' . substr($phone, 1);
    }
    return $phone;
}

// STK Push via Daraja API
$response = sendSTKPush(
    formatPhone($patient_phone),
    $amount,
    $description
);

// Callback updates mpesa_transactions → sets invoice status = 'Paid'
```

#### Snippet C: PDO Prepared Statement — Appointment Conflict Check

A critical safety check that prevents a dentist from being double-booked by checking for existing appointments within a 30-minute window.

```php
$stmt = $pdo->prepare(
    'SELECT id FROM appointments
     WHERE dentist_id = ?
     AND appointment_date = ?
     AND ABS(TIMESTAMPDIFF(MINUTE, appointment_time, ?)) < 30
     AND status NOT IN ("Cancelled")'
);
$stmt->execute([$dentist_id, $date, $time]);

if ($stmt->rowCount() > 0) {
    echo json_encode(['conflict' => true]);
    exit;
}
```

### Appendix VI — Glossary

| Term | Definition |
|---|---|
| **AJAX** | Asynchronous JavaScript and XML — technique for updating page sections without a full reload. |
| **DCMS** | Dental Clinic Management System — the Dr. Smile software suite. |
| **EHR** | Electronic Health Record — the digital collection of a patient's clinical history. |
| **FDI Notation** | Fédération Dentaire Internationale two-digit tooth numbering system (e.g., 16 = upper right first molar). |
| **M-Pesa** | Safaricom's mobile money service, integrated via the Daraja API for STK Push payments. |
| **Ngrok** | Tunnelling service providing a public HTTPS URL for M-Pesa callbacks to reach a local server. |
| **Odontogram** | A graphical diagram of all 32 teeth, colour-coded to show treatment status. |
| **PDO** | PHP Data Objects — secure database library using prepared statements to prevent SQL injection. |
| **RBAC** | Role-Based Access Control — security mechanism restricting users to role-appropriate modules. |
| **STK Push** | SIM Toolkit Push — M-Pesa payment request sent directly to a patient's phone. |
| **UAT** | User Acceptance Testing — final testing performed by end-users to confirm system meets requirements. |
| **XAMPP** | Local web server package (Apache, MySQL, PHP) used for development hosting. |
