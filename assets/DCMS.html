Chapter 1

Background & Problem

Dr. Smile Dental Clinic operated entirely on manual processes — a paper appointment ledger, physical patient file folders, and a spreadsheet for billing. This created a cascade of operational problems that this system was built to solve.

📅

Double-Bookings

No real-time slot visibility meant frequent scheduling conflicts between practitioners, with no automated reminders for patients.

🗂️

Insecure Patient Data

Physical file folders were slow to retrieve, posed security risks, and blocked chairside access to X-rays and treatment history.

🦷

No Clinical Charting

Without an odontogram, procedure charting was subjective and inconsistent, slowing inter-practitioner communication.

💸

Manual Billing

Spreadsheet invoicing introduced errors, slowed financial reporting, and provided no real-time revenue visibility for management.

System Objectives

SMART Goals

Scheduling
Eliminate double-bookings through a real-time, multi-user scheduling interface with automated TIMESTAMPDIFF conflict detection (±30 min buffer).
EHR Retrieval
Enable instant, secure retrieval of any patient's complete Electronic Health Record within 5 seconds via indexed database querying.
Odontogram
Standardise clinical charting via an anatomical SVG Odontogram using the FDI two-digit numbering system with colour-coded treatment status.
Billing
Auto-generate itemised invoices on appointment completion and produce consolidated monthly revenue reports within 3 seconds.
Chapter 3 · Systems Design

Technology Stack

Built on a classic three-tier web architecture using exclusively open-source technologies, keeping the Total Cost of Ownership at zero for the clinic.

Presentation
PHP / HTML5 / CSS3 / JS
'Hygienic Blue' theme. Fully responsive across all browsers.
Application Logic
PHP 8.2 + PDO
RBAC enforcement, business logic, prepared statements.
Data Storage
MySQL Community
Normalised relational schema. Complex EHR & billing joins.
Infrastructure
XAMPP / Cloud + ngrok
HTTPS/TLS delivery. ngrok tunnel for M-Pesa Daraja callbacks.
Payments
M-Pesa Daraja API
STK Push integration for real-time cashless payments.
Security
Bcrypt + AES-256
OWASP Top 10. 30-min session timeout. Immutable audit logs.

Chapter 2 · SRS

Functional Requirements

F1 · Appointment Scheduling
F-1.1
Dynamic calendar views (Day, Week, Month) with Practitioner filter.
User applies filter → view updates instantly.
F-1.2
Prevent double-bookings for same practitioner where time slots overlap within ±30 minutes.
Overlapping attempt → 'Conflict Detected' error; transaction blocked.
F-1.3
Automatically send SMS/Email reminder 24 hours before appointment.
System detects T-24h → API called; status updated to Confirmed.
F-1.4
Receptionist can CRUD appointments and change status.
Status set to Completed → billing module auto-generates invoice.
F2 · Electronic Health Record
F-2.1
Dentists input free-text clinical notes with mandatory electronic sign-off.
Dentist clicks Sign-Off → system timestamps and logs PractitionerID.
F-2.2
Receptionist registers new patients with validated mandatory fields.
Duplicate email → 'Email already registered' alert; submission rejected.
F-2.3
Patient search using partial matches on PatientID, FullName, or ContactPhone.
User types 'Ale' → all matching patients displayed within 2 seconds.
F3 · Odontogram
F-3.1
Display permanent dentition using FDI two-digit numbering system (11–48).
F-3.2
Record procedures against a specific tooth/surface from the Procedure table.
Dentist clicks tooth '37' → modal opens for code selection.
F-3.3
Colour-coding: Green (Completed), Yellow (Planned), Red (Pathology).
Dentist marks as Planned → tooth updates to Yellow instantly.
F4 · Billing & Reporting
F-4.1
Auto-generate itemised invoice when appointment status is set to Completed.
Status = Completed → invoice lists all charted procedures with current fees.
F-4.2
Receptionist records payments, partial payments, discounts, and PDF receipts.
Partial payment → invoice displays updated outstanding balance.
F-4.3
Administrator generates real-time Monthly Revenue Reports (CSV/PDF export).
Admin selects Month/Year → report generated within 3 seconds.

Snippet A — Anatomical Tooth Category Mapping

Maps Universal tooth IDs to anatomical SVG shape categories, ensuring the correct molar/premolar/canine/incisor shape renders for each tooth in the Odontogram.

odontogram.php PHP 
// Maps Universal tooth IDs to anatomical SVG shape categories
if (in_array($tooth_id, [1,2,3,14,15,16,17,18,19,30,31,32])) {
    $category = 'molar';
} elseif (in_array($tooth_id, [4,5,12,13,20,21,28,29])) {
    $category = 'premolar';
} elseif (in_array($tooth_id, [6,11,22,27])) {
    $category = 'canine';
} else {
    $category = 'incisor';
}

// SVG mask applied via CSS:
// mask-image: url('/dcms/assets/img/anatomy/{$category}.svg');

Snippet B — M-Pesa STK Push Integration

Sanitises Kenyan phone numbers to the Safaricom-required 254 format and triggers the Daraja API STK Push for real-time cashless payment collection.

mpesa.php PHP 
// Format phone: 07XXXXXXXX → 2547XXXXXXXX
function formatPhone($phone) {
    if (substr($phone, 0, 1) === '0') {
        return '254' . substr($phone, 1);
    }
    return $phone;
}

// STK Push via Daraja API
$response = sendSTKPush(
    formatPhone($patient_phone),
    $amount,
    $description
);

// Callback updates mpesa_transactions → sets invoice status = 'Paid'

Snippet C — Appointment Conflict Check (PDO)

A critical safety query that blocks double-bookings by checking for existing appointments within a ±30 minute window for the same practitioner using a prepared statement.

appointments.php PHP / SQL 
$stmt = $pdo->prepare(
    'SELECT id FROM appointments
     WHERE dentist_id = ?
     AND appointment_date = ?
     AND ABS(TIMESTAMPDIFF(MINUTE, appointment_time, ?)) < 30
     AND status NOT IN ("Cancelled")'
);
$stmt->execute([$dentist_id, $date, $time]);

if ($stmt->rowCount() > 0) {
    echo json_encode(['conflict' => true]);
    exit;
}
